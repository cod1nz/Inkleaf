# Inkleaf desktop: security review (M9)

Date: 2026-11-01. Scope: `app/` on branch `inkleaf-desktop` (nothing committed). Electron 45.2.1 (latest 45.x), electron-builder 26.18.0.
I read the code and then checked it by running real Electron: the real `main.js` with a Chromium net-log, the bundled pdf.js viewers, and a packaged `--dir` build with fuses in `app/release-sec/`. `app/dist` and `app/release` were not rebuilt or touched.

## Checked and found sound (no change needed)

- **webPreferences:** contextIsolation, sandbox, no nodeIntegration (including subframes), webSecurity, no webview, devtools off when packaged. `window.desk` is the only exposed surface; the smoke test confirms no Node or Electron globals. Sender check: top frame only, app:// origin. Grants are random UUIDs, and the renderer never supplies a path. Writes need a `saveAs` grant and are atomic (temp file with `wx`, then rename). Test hooks only work unpackaged with `INKLEAF_TEST=1`.
- **Navigation:** `will-navigate`, `will-frame-navigate` and `will-redirect` lock to app://. `window.open` is always denied (http(s) goes to the confirm dialog). Probe results: file://, file://UNC, data:, smb: are blocked at top level, a file:// UNC iframe is not loaded, file:// and https fetches fail. Permissions are denied. `webRequest` allows only app/blob/data.
- **Protocol handler:** traversal, encoding, ADS, 8.3, device names and UNC are rejected (22 attack paths in the smoke test). Uses realpath roots. GET/HEAD only.
- **CSP / COOP / COEP** checked in the running app (`crossOriginIsolated === true`, eval blocked).
- **Add-ons:** download is https only, with a redirect host allowlist, a size cap, and hashing before extraction. The zip reader rejects zip-slip, absolute paths, drive letters, backslashes, symlinks or reparse points, special files, duplicates, file/dir conflicts, zip64, encryption, ratio > 200 and executables; it streams with CRC and size checks; files are written `wx` with mode 0644. Sideloading uses a private copy, so the file is the same between hashing and extraction.
- **Zip-slip in the renderer:** cannot happen. The renderer has no filesystem access, and every output goes through a `saveAs` grant and `safeFileName`.
- **Single instance:** argv keeps only `.pdf` args that do not start with `-`. There is no custom URL scheme. No crashReporter or autoUpdater. The only `app.commandLine` switches are the fixed js-flags heap size and the hardening switches above.

## Residual risks

- A compromised renderer still has the full `desk` API: it can read the up to 10 recent files and any file the user opened this session, open save dialogs, and ask for TSA or add-on network use (always behind a consent dialog). It can no longer exfiltrate except through those consented paths.
- Mapped network drives (`Z:`) are not detected as network paths, and paths picked in a dialog are trusted.
- The pdf.js and stash fixes need a rebuilt `dist`. Until then the shipped viewers run PDF JavaScript (inside pdf.js's QuickJS sandbox) and their links are blocked silently rather than confirmed.
- Upstream tool code (459 `innerHTML` sites) relies on its own escaping, with CSP as the backstop.
- Plain-http TSAs (F14). The asar integrity fuse on Windows is still marked experimental by Electron.

## Items needing the user

1. Bump `node-forge` to ^1.4.2 and rebuild `dist` (`npm run build:desktop`). This also activates F3 and F12.
2. Code signing: Windows Authenticode certificate (CSC_LINK / CSC_KEY_PASSWORD) and Apple Developer ID plus notarization secrets. Fuses and asar integrity protect much more on a signed binary.
3. Remove or disable the upstream BentoPDF workflows (F13) before the repo is pushed or published. Replace `REPLACE_ME` in the add-on URL and SHA-256 and in `SOURCE_URL`.
4. Publishing the add-on pack: pin the real SHA-256 and size in `electron/addons/manifest.js`.
5. `app/release-sec/` (my test build, about 185 MB asar) can be deleted. Temp folders `%TEMP%\inkleaf-probe-*` and `%TEMP%\inkleaf-pdfjs-*` from the probes can also be deleted (I was not permitted to sweep %TEMP%).

## Add-on CSP exception: `'unsafe-eval'` for `/addons/` (user-approved)

- **Finding:** the LibreOffice WASM engine (Emscripten/embind, `soffice.js`) builds functions with `new Function`. Under `script-src 'self' 'wasm-unsafe-eval'` its worker died with an EvalError and every Office conversion failed with "WASM initialization timeout".
- **Change:** `ADDON_CSP` in `electron/lib/headers.js` is the normal CSP plus `'unsafe-eval'` in `script-src`. `electron/protocol.js` sends it only on files served from `app://bentopdf/addons/...`; every other response (pages, assets, 404s, errors) keeps the strict CSP. Unit tests assert both, including that non-add-on responses never carry it.
- **Scope and mitigations:** a worker takes its policy from its own script response, so no app page is loosened. Add-on files are SHA-256 verified against the pinned manifest before extraction, extracted with the hardened unzipper, and add-on documents (html/svg/xml/pdf) are refused. Renderer network access is still blocked by the connect-src policy, the webRequest filter and the dead proxy.
- **Residual risk:** code inside the add-on worker can use eval; it is only as trusted as the pinned pack hash.
- **Approval:** the user approved this scoped exception in chat.
